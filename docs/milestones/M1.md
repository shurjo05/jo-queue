# M1: In-memory queue + Go worker pool

## What and why

M1 builds the queue's core behavior with no Redis and no network, so the
rules of a job queue can be learned and tested on their own:

- A **`Job` type** and its four **states**: `queued → running → completed | failed`.
- A **`Queue` interface** (Submit, Claim, Complete, Fail, Get) that every
  later implementation follows: Redis in M2, an HTTP client in M3.
- **`MemoryQueue`**, an implementation of `Queue` held in process memory.
- **`worker.Pool`**, which runs N goroutines that claim, run, and report jobs.
- Two **demo jobs** (`sleep`, `fail`) and a runnable demo in `cmd/worker`.

Writing the worker pool against the interface, not against `MemoryQueue`,
is what lets M2 swap in Redis without touching the pool.

## Key files

| File | What it is |
|------|-----------|
| `internal/queue/queue.go` | `Job`, `State`, the error values, and the `Queue` interface. Start reading here. |
| `internal/queue/memory.go` | `MemoryQueue`: a map of jobs guarded by a mutex, plus a buffered channel of IDs waiting to be claimed. |
| `internal/queue/id.go` | Random 128-bit job IDs from `crypto/rand`. |
| `internal/worker/pool.go` | `Pool` and `Handler`. The claim → run → report loop, panic recovery, graceful shutdown. |
| `internal/jobs/demo.go` | Demo handlers: `sleep` (waits N ms) and `fail` (always errors). |
| `cmd/worker/main.go` | Demo program: submits a batch of jobs to a `MemoryQueue`, runs the pool, prints a summary. |
| `*_test.go` | Tests for each package. All run under `-race` in CI. |

## Data flow

```
 cmd/worker (demo)                       MemoryQueue
 ─────────────────                       ──────────────────────────────────
 Submit(type, payload) ───────────────▶  jobs[id] = {state: queued}   (mutex)
                                         pending <- id                (channel)

 worker.Pool, N goroutines, each looping:
   ┌──────────────────────────────────────────────────────────────────────┐
   │ Claim(ctx) ──────────────────────▶  id := <-pending  (one receiver   │
   │                                      gets each id)                  │
   │                                     jobs[id].state = running        │
   │ handler := Handlers[job.Type]                                       │
   │ err := handler(ctx, job)   (a panic becomes an error)               │
   │ err == nil ? Complete(id) : Fail(id, err) ─▶ state = completed/failed│
   └──────────────────────────────────────────────────────────────────────┘
```

## Decisions

- **Buffered channel for pending jobs, mutex for job records.** A Go channel
  hands each value to exactly one receiver, so "no job is claimed twice"
  comes for free and `TestNoDoubleClaim` (16 goroutines, 2000 jobs) checks
  it. The map of records still needs a mutex, because many goroutines read
  and write it. In C# terms: the channel is like a `BlockingCollection<T>`
  or `Channel<T>`, and the mutex is `lock`.
- **Bounded queue: `Submit` returns `ErrQueueFull` instead of blocking.**
  Capacity defaults to 1024. Rejecting work when full (backpressure) is
  more honest than blocking the caller or growing memory without limit. Redis
  in M2 has no small fixed bound, so this limit is specific to `MemoryQueue`.
- **Only a running job can be completed or failed** (`ErrInvalidState`
  otherwise). This blocks double-completes and "complete after fail" bugs,
  which matter more once leases (M5) let a job run twice.
- **Copies in, copies out.** `Submit` copies the payload and `Claim`/`Get`
  return deep copies, so no caller can change the queue's records without
  holding its lock.
- **`Claim` checks for cancellation before waiting.** Building M1 surfaced a
  real bug here: when a job is waiting *and* the context is already
  cancelled, Go's `select` picks a ready case at random, so a worker that
  was shutting down could still grab a new job. `Claim` now checks
  `ctx.Err()` first, and the pool checks it before every claim.
  `TestPoolShutdownFinishesRunningJob` and
  `TestClaimWithCancelledContextLeavesJobQueued` cover this.
- **Graceful shutdown.** Cancelling the pool's context stops new claims, but
  a job already running finishes and reports its result. The handler gets
  `context.WithoutCancel(ctx)` so shutdown doesn't abort it halfway.
- **A panicking handler fails its job, not the process.** `recover()` turns
  the panic into an error (with stack trace) stored in `LastError`.
- **Unknown job type → job failed** with "no handler registered", not a crash
  and not left running forever.
- **Random IDs, no UUID library.** 16 bytes from `crypto/rand` as hex.
  No coordination needed between servers, and no dependency.
- **No retries yet.** `failed` is final in M1. Retries with backoff are M4.
- **Structured logging with the standard `log/slog`**, no third-party logger.

## How to verify (Windows 11, PowerShell)

```powershell
git checkout main; git pull

go vet ./...
go test ./...                       # ok for internal/jobs, internal/queue, internal/worker
go test -v -run NoDoubleClaim ./internal/queue

# Demo: 20 jobs, every 5th fails on purpose, 200ms per sleep job.
go run ./cmd/worker -workers 4      # expect about 0.8s: 16 completed, 4 failed
go run ./cmd/worker -workers 1      # expect about 3.2s: same counts, one at a time
go run ./cmd/worker -jobs 200 -workers 50 -sleep 100ms -fail-every 0
```

The time scales with workers as expected: 16 sleep jobs × 200ms ≈ 3.2s
with 1 worker, ≈ 0.8s with 4. These are rough numbers from one run of a
synthetic job; real benchmarks come in M7.

Press Ctrl+C during a long run (`-jobs 1000 -workers 2`) to see graceful
shutdown: running jobs finish, the rest stay `queued`.

## Limitations

- **Nothing survives a restart.** Jobs live in one process's memory.
  Redis (M2) fixes this.
- **One process only.** Workers must be goroutines in the same program as
  the queue. The HTTP server (M3) lets separate processes share a queue.
- **A crashed handler is caught, but a crashed process loses its jobs.**
  Running jobs in a killed process are simply gone. Leases (M5) recover them.
- **No retries** (M4) and **no idempotency keys** (M6).
- **`MemoryQueue` never forgets finished jobs**, so memory grows with every
  job submitted. Fine for tests and demos.
- **`cmd/worker` is a self-contained demo** for now. In M3 it becomes a real
  worker that talks to the queue server.
