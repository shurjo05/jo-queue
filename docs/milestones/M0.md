# M0: Project skeleton

## What and why

M0 builds no queue features. It sets up everything that later milestones
rely on, so that from M1 onward every change is code plus tests:

- A **Go module** (`github.com/shurjo05/jo-queue`), so packages can import each other.
- The **folder layout** from decision D5, with placeholder programs.
- **Redis in Docker Compose**, so a local Redis is one command away (used from M2).
- **GitHub Actions CI** that checks formatting, vets, builds, and runs tests
  with the race detector on every push and pull request.

## Key files

| File | What it is |
|------|-----------|
| `go.mod` | Declares the module path and the minimum Go version (1.24). Like a `pyproject.toml` or `.csproj`. No dependencies yet. |
| `cmd/server/main.go`, `cmd/worker/main.go`, `cmd/cli/main.go` | Three separate programs. In Go, every folder under `cmd/` with `package main` and a `main()` builds into its own executable. Each prints "not implemented yet". |
| `internal/queue/doc.go` | Package documentation only. `internal/` is enforced by the Go compiler: code outside this module cannot import it. |
| `internal/queue/smoke_test.go` | A throwaway concurrent test so CI's `go test -race` has something to run. Removed in M1. |
| `compose.yaml` | Runs `redis:7.4-alpine` on port 6379 with a health check and a named data volume. |
| `.github/workflows/ci.yml` | Two CI jobs: `test` (gofmt, vet, build, `test -race`) and `compose` (starts Redis, waits for healthy, pings it). |

## Data flow

None yet. The planned flow (M3 onward) is:

```
CLI / producer ──HTTP──▶ server ──▶ Redis ◀── server ◀──HTTP── workers
```

## Decisions made in M0

- **Placeholder `main` in each `cmd/` folder** rather than empty folders. Git
  doesn't track empty folders, and real `main` packages prove the layout builds.
- **No Redis client library yet.** Adding a dependency we don't call would be
  noise. The Go Redis client (`go-redis`) comes in M2.
- **Redis with `appendonly yes`.** Redis keeps data in memory. By default it only
  takes periodic snapshots, so a crash could lose recently submitted jobs. The
  append-only file logs each write and flushes it to disk about once per second,
  so at most around one second of writes can be lost. That's a sensible default
  for a queue. Exact durability tradeoffs are a topic for M5.
- **Redis 7.4 pinned to a minor version** so a surprise major upgrade can't
  change behavior under us.
- **`go test -race` runs in CI, not required locally.** The race detector is
  built on a C library, so on Windows it needs cgo and a C compiler (MinGW-w64).
  Linux CI runners have one by default.
- **gofmt is enforced in CI.** Go has one official format, so there is no style debate.
- **No Makefile.** `make` isn't on Windows by default; plain `go` and `docker`
  commands work everywhere.

## How to verify (Windows 11, PowerShell)

From the repo root:

```powershell
go version                 # expect go1.24 or newer

go vet ./...               # no output means no problems
go build ./...             # compiles all packages; no output means success
go test ./...              # expect "ok  github.com/shurjo05/jo-queue/internal/queue"

go run ./cmd/server        # prints: jo-queue server: not implemented yet (planned for M3)
go run ./cmd/worker
go run ./cmd/cli

docker compose up -d --wait               # starts Redis and waits until healthy
docker compose ps                         # STATUS should say "healthy"
docker compose exec redis redis-cli ping  # PONG
docker compose down                       # stop; add -v to delete stored data
```

`./...` means "this folder and every folder below it".

Optional, to run the race detector locally: install a MinGW-w64 gcc (for
example with `winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT`), open a
new terminal, then:

```powershell
$env:CGO_ENABLED = "1"
go test -race ./...
```

To see the race detector catch a bug, remove the mutex from
`internal/queue/smoke_test.go` (the `mu` variable and its `Lock`/`Unlock` calls)
and run `go test -race ./...` again: it reports `WARNING: DATA RACE` and fails.

On GitHub, the **Actions** tab shows both CI jobs passing on the M0 pull request.

## Limitations

- No queue behavior at all. The three programs only print a message.
- The smoke test checks the CI pipeline, not jo-queue. It is deleted in M1.
- Redis has no password and listens on `localhost:6379`. That's fine for local
  development only (auth is out of scope for this project).
- The `compose` CI job was not run locally while building M0 (no Docker daemon
  in the build environment). CI on the pull request is its first real run.
